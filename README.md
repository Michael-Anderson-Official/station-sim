# 駅シム — 1面1線から新宿へ

しょぼい 1面1線の駅を、乗客をさばきながら新宿級の巨大ターミナルまで育てる3D経営シム。
Three.js（`three.min.js` をローカル同梱、CDN不要）。

## 遊ぶ

https://michael-anderson-official.github.io/station-sim/

PCから配信する場合は `play-on-phone.bat` をダブルクリック → 表示されたURLをスマホ（同じWi-Fi）で開く。

```bash
node serve.mjs
```

PCだけで遊ぶなら http://localhost:8370

## 乗客は駅の周りを開発しないと増えない

街が勝手に発展することはない。🏗増築 →「周辺開発」で用途を建てて初めて需要が生まれる。
開業時にあるのは小さな住宅地ひとつ（900人/日）だけ。

| 用途 | 1日の乗降 | 時間帯の形 | 必要な評判 |
|---|---|---|---|
| 🏘 住宅地 | 900 | 朝に出て夜に帰る。1日を通して | — |
| 🏫 高校 | 1,800 | 朝が鋭く、帰りは夕方前 | 52 |
| 🏢 オフィス | 2,600 | 朝の降車と夕方の乗車に集中 | 58 |
| 🏬 商業施設 | 4,200 | 昼から夕方に広く分布 | 64 |
| 🎓 大学 | 7,500 | 高校より規模が大きい | 70 |
| 🏙 高層オフィス | 16,000 | 朝夕のピークが一段跳ねる | 76 |
| 🌆 ニュータウン | 26,000 | 沿線人口そのものを増やす | 80 |
| 🌃 副都心開発 | 200,000 | 新宿級に到達する唯一の道 | 86 |

用途ごとに**乗車と降車を別々の時間帯カーブ**で持っている。住宅地は朝に乗る人が多く、
オフィスは朝に降りる人が多い。だから同じ「1日◯人」でも、ダイヤに要求するものが違う。

評判が高いほど実際に使う人が増える（0.55〜1.30倍）。評判は満足度で決まるので、
**良い駅を運営する → 開発が解禁される → 需要が増える → もっと良い駅が要る** という順になる。

実測（住宅地4 + 高校1 の駅に、オフィスを2つ足したとき）:

| ダイヤ | 乗降 | 満足度 |
|---|---|---|
| 6両20分毎・1線 | 2,533 | 37 |
| 8両5分毎・2線 | 12,162 | 99 |

オフィスを足しただけでは**乗降が減る**。朝夕に需要が集中するので、
20分毎では捌けず積み残しが出て評判が落ちるため。増発して初めて開発が実る。

## 列車は契約してダイヤを組む

自動では一本も来ない。**列車を契約し、自分でダイヤを引いて初めて動き出す。**

ダイヤは**番線ごとに編集する**。上のタブで番線を選ぶと、その番線のスジだけが並ぶ。
置きかたは2通りある。

**⚡＋1本（臨時列車）** — 契約なしで1本だけ走らせる。他社から1本借りる扱いで、
走らせるごとに借り賃（その形式のリース料の1/8）を払う。開業直後でも押せる。

**＋パターン** — 契約した編成で「5:00〜24:00・12分毎・普通・停車45秒」のような
繰り返しを1行置く。1行が1日ぶんのスジに展開される。

| | 初期費用 | 1本あたり | 向いている場面 |
|---|---|---|---|
| 臨時（＋1本） | なし | 運行費 + 借り賃（リース÷8） | 試運転、朝夕だけの増発、開業直後 |
| 契約＋パターン | 車両価格（¥38万〜） | 運行費のみ（+ 日次リース） | 終日運行。1形式8本/日を超えたらこちら |

帯を横にドラッグすると動く（臨時はその1本だけ、パターンは全体がずれる）。
行をタップすると種別／編成／番線／時刻／停車を調整できる。

### 番線の進行方向

番線ごとに**北行き／南行き**を決める。列車は選んだ向きの端に先頭を揃えて停まり、
その向きへ発車する。**発車間隔で競合するのは同じ本線の同じ向きだけ**で、
逆方向は別の線路なので互いに影響しない（実際の上り本線・下り本線と同じ）。

**停車時間が詰め込み量を決める。** 停車を延ばせば多く乗せられるが、
その分だけ発車が遅れて後続に響く。乗車は定刻で打ち切られる（＝積み残し）。
遅延になるのは「降車が終わらない」ときと「前の列車が抜けていない」ときだけ。

### 本線と番線 — 輸送力の決まり方

発車間隔の制約は2本立てになっている。

| | 最短間隔 | 理由 |
|---|---|---|
| 同じ**本線の同じ向き**（駅の外へ出ていく線路） | 1分 | 信号の間隔 |
| 同じ**番線**（ホームの線路） | 2分 | 停車＋進入退出 |

```
輸送力 = min( 本線数 × 2方向 × 60本/時 , 番線数 × 30本/時 )
```

つまり**同じ向きの2番線を交互に使うと1分間隔が出せる**。京王線の桜上水（2面4線）が
3番線と4番線を交互に使って1分間隔を実現しているのと同じ構造。

実測（8時台の発車本数。同じ向きの番線どうしは発車をずらしてある）:

| 構成 | 本/時 |
|---|---|
| 1面1線・1本線・北 | 30 |
| 1面2線・1本線・北北 | 60 |
| 1面2線・1本線・北南 | 60 |
| 2面4線・1本線・**全部北** | 60（本線の片方向が上限） |
| 2面4線・1本線・北北南南 | **120** |
| 3面6線・1本線・北3南3 | 120（本線が上限） |
| 4面8線・2本線・各北2南2 | **240** |

番線だけ増やしても頭打ちになるし、全部を同じ向きにしても頭打ちになる。
番線数・本線数・上下の振り分けの3つを噛み合わせる必要がある。

### 待避が必要になる理由

**同じ本線では追い越しが起きない。** 遅い種別の直後に速い種別を出すと追いついて
しまうので、8分空ける必要がある（それ以外は1分まで詰められる）。

つまり**急行の直前に普通は出せない**。普通を別の番線に停めて先に急行を行かせる、
という待避がダイヤ上の解になる。実測でも 普通→急行を4分ずらしだと71件のエラー、
8分ずらしで0件になる。

乗客の35%は優等が走っていると「速い列車を待つ」ようになり、普通には乗らない
（12分待つと妥協する）。優等は運賃の取り分も大きい（普通1.00 / 急行1.15 / 特急1.60）。

### 収支は3層

| | いつ | 何で決まる |
|---|---|---|
| 契約金 | 契約した瞬間 | 形式の単価 × 両数 |
| リース | 毎日 | 保有している編成すべて |
| 運行費 | 発車ごと | 両数 × 900円 ×（種別で増）|

本数を増やせば運賃収入は増えるが、運行費も比例して増える。
日報が損益計算書になっているので、どこで負けているかが見える。

## ゲームの流れ

1. 列車が到着 → 乗客が降りる。降車客は **ホーム → 階段 → コンコース → 改札 → 出口** を歩く
2. 入場客は逆に **駅前 → 改札 → 階段 → ホーム** を歩き、列車を待って乗る
3. 乗降1人ごとに運賃の駅取り分が入る（駅ナカ店舗があれば副収入も）
4. 駅内の滞在時間が長いほど乗客の満足度が下がる → **評判** が下がる
5. 評判が高いと **街が発展** して needs が増え、また混む → 増築、のループ
6. 1日の乗降客数で駅ランクが上がる（無人駅 → … → 新宿級 = 300万人/日）

### 詰まるポイント

| 設備 | 処理能力 |
|---|---|
| 手動改札（駅員） | 1通路 約2.8秒に1人。安いが人件費 ¥42,000/日 |
| 自動改札 | 1台 約1.4秒に1人。初期費用は高いが維持費は安い |
| 階段 | 1つ 約0.85秒に1人（エスカレーター化で約2倍） |
| ホーム有効長 | 着けられる編成の長さを決める。2両 〜 15両 |
| 停車時間 | ドア扱い量 × 停車秒数 までしか乗せられない |
| 線路 | 同じ番線は前の列車が抜けるまで使えない（30秒の間隔） |
| ホーム幅・コンコース幅 | 混雑密度 → 歩行速度に影響 |

ホームが短いと階段も置けない（50mにつき1つ、最大6つ）ので、
**延伸は「輸送力・運行本数・階段の数」の3つを同時に開ける**。

**開業時は田舎のごく小さな地平駅**。ホームと線路が1本ずつあるだけで、
駅舎も構内踏切も階段も無い。ホーム端から地面へ下りるとそこが駅前。
改札は🗺配置で**ホームの上に直接置く**（駅舎は無い）。
改札が1つも無いあいだは運賃を45%取りこぼすので、まずは安い手動改札から。
乗客が増えると駅員の人件費と処理速度が効いてきて、自動改札への置き換えが必要になる。

ホームが1面のうちは線路を渡る必要が無いので、詰まるのは改札とホームの幅だけ。
2面以上に増やすには動線を立体化する。**橋上駅舎**か**地下道**のどちらかを選ぶ。

| | 建設費 | 特徴 |
|---|---|---|
| 🌉 橋上駅舎 | ¥980万 + 線路数 | 高いが明るく、階段の増設が安い |
| 🕳 地下道 | ¥520万 + 線路数 | 安く済むが、階段の増設が1.5倍かかる |

どちらを建てるとコンコースができ、階段がボトルネックとして登場し、
ホームを2面以上に増やせるようになる。改札や店はコンコースにも置ける。

実測（3面6線・10両・街の発展70の朝ラッシュ）:

| 改札 | 満足度 | 改札待ち最大 | 駅前滞留 |
|---|---|---|---|
| 手動8 | 19 | 755秒 | 5057人 |
| 自動8 | 59 | 451秒 | 2609人 |
| 自動20 | 77 | 318秒 | 1049人 |

満足度は「駅の中で無駄に過ごした時間」で決まる。次の列車を待つ時間そのものは
駅のせいではないので除外し、**1本乗り遅れた（積み残された）分だけ**を罰する。

処理能力を超えると駅に入りきらず **入場規制**（駅前に行列）になり、
待たされすぎた客は諦めて帰る＝評判に直撃する。

## 乗客はどこを歩くか — 盤面の距離場

駅は 1マス2m のグリッド（176×224×2層）で持っていて、**乗客の歩行もその盤面の上で
決まる**。目的地の集団（出口の帯／改札1行の口／ホームごとの階段列）ごとに
多始点の幅優先探索で距離場を焼き、乗客はその勾配を下って歩く。

大事なのは**端から端までの距離場を張らないこと**。改札は盤面上で壁になっていない
（改札セルの左右に床が残る）ので、「出口→ホーム」を一発で探索すると全員が改札を
迂回できてしまい、待ち行列＝経済が静かに消える。距離場が案内するのは、いま向かって
いる設備の集団までに限っている。

階段はレイヤー0にしかセルが無いので、層をまたぐ辺は通行マスクの bit1（縦ポータル）
で表す。ただし**ポータルは距離を伝播させるためだけ**にあり、実際の昇り降りは
従来どおり `climb` ノードが担う。高さの変わる脚では距離場を使わない。

| 構成 | 歩行可能セル | 距離場 | 再構築 |
|---|---|---|---|
| 開業 地平1面1線 | 135 | 3枚 | 0.9ms |
| 橋上 2面4線 | 1,001 | 7枚 | 1.2ms |
| 地下 10面20線（新宿級） | 7,809 | 17枚 | 2.3ms |

再構築は増築のときだけ走る。距離場は Uint16Array 1枚154KiB で、最大構成でも4MiB弱。

## デバッグ

ブラウザのコンソールから：

```js
sim.step(3600)     // 1時間進める
sim.buy('cars')    // 増築（id: cars/gateM/gateA/bridge/under/stairs/esc/track/plat/platw/conc/shop）
sim.hire('mei6000', 2, 1)                       // 契約（形式, 両数, 本数）
sim.addDia({m:'mei6000',cars:2,ty:0,track:0,
            from:5*60,to:24*60,every:30,dwell:45})  // パターン追加（時刻は分）
sim.dia()          // 契約とダイヤの一覧、所要/契約本数、問題
sim.compile()      // ダイヤだけ組み直して {slots, issues} を返す
sim.S.runs         // 1本ずつ置いた臨時スジ [{id,m,cars,ty,track,at(分),dwell}]
sim.S.trackDir     // 番線 → 進行方向 0=北行き(+Zへ発車) / 1=南行き
sim.S              // 状態
sim.three          // renderer / scene / camera
sim.ui             // ダイヤ編集UIの状態
sim.rebuild()      // S を直接いじった後にレイアウトとダイヤを反映
sim.reset()        // セーブ削除して再読み込み
```

`S.t` を戻してから `rebuild()` を呼ぶこと。逆順にするとスジのカーソルが
進んだままになり、その日の列車が一本も来なくなる。

歩行グラフ（盤面の距離場）まわり：

```js
sim.walkStats()    // 静的検査。乗客を1人も動かさずに盤面の健全性を測る
sim.walkSweep()    // 開業から新宿級まで9構成を順に組んで各段で walkStats
sim.useField(false)// 距離場をやめて従来の直線歩行に戻す
sim.anchor(false)  // ノードの目標座標をパラメトリック値に戻す
sim.audit(true)    // 影エージェント(距離場だけで動く2つ目の位置)を並走させる
sim.auditReport()  // 影と本体の差、脚の終わりの到達距離、脚の種類別の内訳
sim.resN()         // res(階段/改札/踏切)の取得回数。歩き方を変えても不変であるべき
sim.seed(12345)    // 種付き乱数。同じ種なら同じ客列になり、歩き方だけを比較できる
sim.wk             // WK 本体(pass/fields/platRect/gateMouth/stairTop ほか)
```

`walkStats()` で見るべき値は **`platUnreach` と `runGap` と `portalPairs`**。
それぞれ「ホームに届かないセル」「設備へ寄る直線の途中にある障害物」
「階段の層間接続」を表し、どれか1つでも0でなくなったら盤面レイアウトが壊れている。

画面を直接見られない環境用に、描画結果をPNGで書き出せる。
`node serve.mjs --dev` で起動し、`?dev=1` を付けて開いてから:

```js
await sim.shot(1280, 800, 9)   // 幅, 高さ, 時刻 → shot.png に保存
```

### 盤面まわりの注意

- **`B.o`（セル→設備ID）は逆引きに使えない。** `placeFac` が無条件に上書きするので、
  あとから置いた設備が先の設備のセルを奪う。逆引きは必ず `B.objs` から作る。
  改札と階段のセルは `placeFac` のガードで守っているが、店や自販機同士は今も奪い合う。
- **`gridFromParams()` の座標式を他の場所で再現しない。** ホーム矩形は `C_PLAT` の
  x連続区間、出口は `C_ENTRANCE` の外接、踏切は `F_CROSS` の外接、番線→乗車列は
  `DV.tracks` から、いずれも**盤面を走査して**求める。式が2箇所にあると、
  レイアウトを変えたときに静かに1〜2セルずれる。
- **通行不可の補修を `B.t` に書かない。** `greedyRects` が拾って3Dの外形が変わる
  （床として書いた所は 3D でも床や壁として拾われる）。
  補修も店舗の除外も `WK.pass` だけを触ること。
- **`cx()` / `cz()` を `|0` に最適化しない。** `OX=88` なので盤の西半分は常に `X<0`
  で、ゼロ方向切り捨てだと1マスずれる。

### 描画まわりの注意

同梱の three は ColorManagement が無い世代なので、マテリアルに16進色を直接渡すと
リニア値として扱われ ACES を通って白飛びする。色は必ず `C(0x……)`
（`convertSRGBToLinear`）を通すこと。空の ShaderMaterial も
`tonemapping_fragment` / `encodings_fragment` を自前で include している。

## 調整メモ

バランスの主なつまみは `game.js` 冒頭の `CFG` と：

- `demandPerSec()` の `base`（初期需要。現在 120人/時）
- `endOfDay()` の `growth`（街の成長率。現在 評判90で約33%/日）
- `RANKS`（ランクの必要乗降客数）
- `trainHeadway()`（運行間隔。ランクと編成長で決まる）
- `CFG.LOAD_ROOM` / `CFG.ALIGHT_ROOM`（到着した列車の空き具合＝積み残しやすさ）

貪欲AIで通した実測では、2両1面1線のまま放置すると5日目あたりから満足度が落ちはじめ、
7日目には92まで下がる。延伸・増線すると回復する。
